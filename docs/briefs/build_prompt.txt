BUILD PROMPT: FINE-TUNE A BUSINESS ANALYSIS AGENT WITH LEXSI TOOLS

You are my ML engineering partner. Implement a focused business-analysis agent for Track 3, Agentic Fine-tuning, of the Lexsi AI Safety and Alignment Hackathon. Start from the existing project and work toward a functioning trained agent, a fair before/after evaluation, and a clear demonstration. Research supports implementation; the next goal is executable progress.

OBJECTIVE

Build a small agent that reads business evidence, formalizes the decision, uses tools to select worthwhile investigations, incorporates their results, and makes a justified product-launch recommendation under a research budget.

Fine-tune its underlying permitted Cohere model using AgentTune. Evaluate the base and fine-tuned model using AuditKIT plus our verifiable business metrics. Measure whether training reduces errors and wasted investigations while improving decisions. Improvement is a hypothesis to test, not a result to promise.

The first version covers one decision: whether to launch a product. It is a simulated business-analysis environment with explicit assumptions and known scoring. Do not expand into a general consulting platform, investment adviser, autonomous company, or large multi-agent system.

IMPLEMENTATION PLAN

Phase 1 — Resolve access and prove the real-model path.

Inspect the existing environment and reproduce the relevant existing checks once. Load the real permitted checkpoint and tokenizer with a feasible precision/quantization configuration. Complete a forward pass, one model-generated valid tool call, and a short episode ending in a model-chosen decision. Then run one genuine optimizer step through the intended AgentTune training path. Verify finite loss, meaningful gradients, and saved/reloaded adapter behavior. Toy-model probes do not replace these checks.

If access is blocked, identify the exact user action needed without revealing tokens. Continue environment and dataset work while waiting. Never automatically delete caches or change shared environments. Estimate training resources only after measuring real-model behavior.

Phase 2 — Complete the task and tool interface.

Implement one agent with these tools, adapting names to existing code where sensible:
- read_case: returns a simulated memo, study descriptions, decision objective, and constraints.
- set_problem: records the agent's structured interpretation of the case.
- plan_investigation: computes possible investigations and stopping values from the agent's supplied model.
- run_study: spends a specified research cost and returns a simulated observation/report.
- record_result: records the agent's interpretation of an observation and updates its supplied model.
- finish: records the actual launch/do-not-launch recommendation, explicit probabilities, evidence references, assumptions, and limitations.

Fix the current schema mismatch before implementing the harder task. One prior_viable probability with binary study likelihoods cannot generally preserve the demand/capability information needed by the conjunctive family. Represent named joint hypotheses, a prior probability vector, payoffs for each action/state, study likelihoods by hypothesis, and costs/budget. Validate dimensions, normalization, probability bounds, and finite values. Use the existing Scenario representation if appropriate.

The planning tool must support the declared planning horizon; do not silently expose only myopic values in a task designed to require lookahead. Its calculations use the agent's extracted inputs, not hidden answer keys. This allows extraction mistakes to affect the workflow and remain measurable.

Preserve research spending and observation history across calls. Prevent resetting a budget through set_problem, double-recording an observation, fabricating an observation, or reusing an expired study result. Give observations unique IDs and validate their use. Do not supply hidden states, seeds, correct structured inputs, or evaluator objects to the model.

An insufficient-evidence statement may describe uncertainty, but it still needs a defined operational consequence and score. Do not give abstention a free pass. Match the final recommendation to the agent's own action; never silently substitute the planner's better action during evaluation.

Phase 3 — Build a small but meaningful benchmark and run the base agent.

Create cases with business memos and study reports rendered into prose from known synthetic scenarios. Cover:
- Research is useful versus stopping immediately is best.
- Informative but irrelevant evidence.
- Tight budgets and redundant or uninformative studies.
- Demand and capability requiring complementary investigations.
- Contradictory observations and noisy studies.
- Changed study names, likelihoods, wording, and number formats.
- Matching cases with a manager advocating launch versus opposing it, while actual evidence is unchanged.

Only the case narrative and tool responses go to the agent. Keep initial assumptions distinct from observations. Label synthetic content clearly. The final test must use untouched scenario instances and held-out narrative templates; do not count multiple fields or paired versions of one scenario as independent observations.

Run 5-10 smoke cases first. Then use a bounded exploratory base-model pilot, initially around 30-50 underlying scenarios if runtime permits. Compare a reasonable prompt with a stronger workflow prompt using schema validation and a fixed retry budget. Include the simple parser-plus-planner and correct-input planner as controls. Record concrete errors before choosing what to train.

If the strongest prompt already solves the benchmark reliably, report that finding and identify a practically relevant remaining difficulty. Do not manufacture arbitrary complexity merely to make a model fail.

Phase 4 — Create verified demonstrations and fine-tune.

Use the planner and executable checks to create correct structured tool trajectories. Pilot with roughly 200-500 verified training episodes if resources permit; these are starting caps, not mandatory dataset sizes or guaranteed adequate samples. Keep validation and test cases separate before generation.

Use varied business wording and include correct stopping, supported launches, rejected launches, and uncertainty. Each trajectory needs source scenario ID, generator version, observations, actions, and verification status. Avoid paper text and confidential material. If using a language model to paraphrase cases, verify all numerical and causal facts against the original scenario.

Verify AgentTune's expected trajectory schema and loss masking. Train on the assistant's intended actions/outputs, not hidden oracle fields or accidental tool-result targets. First overfit a tiny diagnostic set to check the pipeline, then run one bounded supervised pilot with LoRA/quantization if actually supported. Freeze the final training configuration before final evaluation. Keep all failed runs visible.

Phase 5 — Evaluate the saved adapter against the strong baseline.

Reload the saved adapter and evaluate it using AuditKIT on the same tasks/tools/budgets as the base model. Preserve real EventLogs and implement project-specific scoring explicitly. Check the existing bridge gotcha: a finish tool call may not populate episode.final_answer; evaluate the actual finish event rather than marking every episode as failed.

Primary outcome: decision value after research costs, or loss relative to the defined Bayesian planner. Score the action actually taken. Define the planner's information and integrate observation noise where tractable; a single terminal path can outperform its initial expected-value reference by chance, so aggregate appropriately.

Secondary outcomes: exact field interpretation, valid tool calls, task completion, unnecessary spending/calls, probability accuracy/calibration, latency, and tokens. Separate business decision quality from format compliance. Charge research cost once. Report confidence intervals clustered by underlying scenario and the effective sample size. Fix the final evaluation size before seeing final-test outcomes; if resources limit precision, say so.

The required comparison is strongest prompted base model versus fine-tuned same model with the same workflow. Larger models and classical controls are additional references. Report negative results, overhead, and cases where training hurts. Never claim improvement from one optimizer step, parameters changing, lower training loss alone, or a cherry-picked demonstration.

Phase 6 — Prepare a clear demo and submission materials.

Create a simple CLI or small interface showing the memo, extracted assumptions, tool calls, study costs, observations, final recommendation, and uncertainties. Show original and trained agents on the same cases without exposing hidden answer keys in their prompts.

Prepare a concise README, reproducible commands, pinned versions/revisions, model/adapter card, dataset card, before/after table, limitations, and an HF Article draft following the current checklist. Separate public deliverables from the private repository's PDFs, extracts, logs, and credentials. Prepare publication locally; do not publish without explicit authorization.
